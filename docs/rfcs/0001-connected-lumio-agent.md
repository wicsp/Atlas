# RFC 0001: Connected Lumio Agent

- **Status:** Proposed
- **Owners:** Atlas and Lumio
- **Target:** First cross-repository vertical slice
- **Protocol:** `atlas-agent-v1`

## Summary

Connect an active pi session with Lumio loaded to Atlas as an observable agent. The session
registers at startup, sends bounded heartbeats while it is active, advertises a small capability
set, and becomes offline naturally after its heartbeat TTL expires.

This RFC validates the Atlas/Lumio/`nix-config` boundaries before introducing durable jobs,
artifact transfer, background workers, or Atlas Console development.

## User outcome

From Atlas, the operator can answer:

- Is a Lumio-enabled pi session currently available on the Mac?
- Which version and revision is it running?
- Which high-level capabilities does it advertise?
- When was it last seen?

Atlas unavailability must not prevent pi from starting or Lumio from performing local work.

## Scope

### Included

- Use the existing Atlas agent registration and heartbeat endpoints.
- Add a narrow Atlas client boundary in Lumio.
- Register an active pi/Lumio session during its lifecycle.
- Heartbeat periodically while that session is alive.
- Report non-sensitive version, node, runtime, and capability metadata.
- Supply endpoint and credential references through host configuration.
- Verify online-to-offline behavior end to end.

### Excluded

- Job creation, leasing, retries, and result reporting.
- Background Lumio workers that survive after pi exits.
- Message consumption or remote prompt execution.
- Atlas Console UI work.
- Node persistence as a new Atlas domain object.
- Per-agent tokens in this first compatibility slice.
- Source, Resource, Artifact, or KnowledgeComment APIs.

Those exclusions are deliberate. The first slice proves connectivity and lifecycle semantics only.

## Existing Atlas API

The current source already provides:

```text
POST /api/agents/register
POST /api/agents/{agent_id}/heartbeat
GET  /api/agents
GET  /api/health
```

No new persistence model is required for the first implementation. Registration metadata can use
the existing `metadata` JSON field.

## Agent identity

An interactive session is not a permanently online host daemon. Use an identity that makes this
clear and avoids two sessions overwriting each other:

```text
<node>.lumio.pi.<session-id>
```

Example:

```text
macsp.lumio.pi.01j2example
```

The session ID should be generated by pi or Lumio and contain no username, working-directory path,
prompt content, or secret. A future persistent worker will have a different identity, for example
`amax.lumio.worker`, and requires a separate RFC.

## Registration payload

Illustrative payload:

```json
{
  "agent_id": "macsp.lumio.pi.01j2example",
  "name": "Lumio pi session on macsp",
  "capabilities": [
    "resource.bilibili.transcript"
  ],
  "metadata": {
    "node_id": "macsp",
    "runtime": "pi",
    "runtime_version": "<pi-version>",
    "lumio_version": "<lumio-version>",
    "git_revision": "<lumio-revision-or-null>",
    "protocol_version": "atlas-agent-v1",
    "interactive": true
  }
}
```

Capability names describe stable outcomes, not implementation details. Do not advertise a
capability until its invocation contract exists. The first implementation may advertise an empty
list if Bilibili capability naming has not yet been stabilized.

## Lifecycle

1. Lumio starts normally without waiting for Atlas.
2. After pi session startup, Lumio attempts registration with a short timeout.
3. On success, Lumio begins a heartbeat loop.
4. Heartbeats run every 30 seconds by default, less than the current 90-second Atlas TTL.
5. Failures are logged concisely and retried with bounded exponential backoff.
6. Atlas marks the agent offline after TTL expiry; explicit deregistration is unnecessary.
7. Session shutdown stops the local heartbeat loop.

Atlas connectivity must remain optional. Startup, local tools, and session shutdown must continue
when Atlas is unreachable.

## Lumio configuration

Suggested environment contract:

```text
ATLAS_URL=https://<private-atlas-endpoint>
ATLAS_AGENT_TOKEN_FILE=/run-or-user-secret-path/atlas-agent-token
ATLAS_NODE_ID=macsp
```

Read the token from a file rather than putting it in a command-line argument. Lumio must not print
the token, request Authorization header, or full environment in logs or tool output.

If the URL or token file is absent, integration is disabled without warning on every session. A
single concise status message or `/atlas status` command is sufficient for diagnosis.

## Atlas implementation work

Before exposing the source implementation as the real service:

1. Use baseline commit `4b79af1` (`chore: establish atlas baseline`) as the rollback anchor.
2. Verify `atlas.main:app` on a temporary port.
3. Confirm that the agent SQLite path is persistent and excluded from Git.
4. Run the current agent API/service tests.
5. Deploy the new entry point under a service manager.
6. Keep the canary isolated to a localhost systemd user service and a detached `4b79af1`
   rollback worktree.

For this RFC, Atlas keeps bearer-token authentication for the agent API, but the token is supplied
out of band through environment or secret-file wiring. It does **not** authenticate the claimed
`from_agent_id`. Per-agent credentials and server-derived identity are mandatory before Atlas
accepts security-sensitive jobs or remote execution, and `config/atlas.toml` must not carry a
shared token value.

## Lumio implementation work

Add one small Atlas adapter rather than spreading HTTP calls through extensions:

```text
extensions/atlas/
  client.ts
  session-agent.ts
  status.ts
```

Exact names may change to fit Lumio conventions. The boundary should provide:

- configuration parsing and validation;
- registration;
- heartbeat;
- concise status inspection;
- timeout, retry, and cancellation behavior;
- redacted diagnostics.

Register it through the normal Lumio extension index. It must not add a large runtime dependency;
the platform HTTP client is sufficient.

## nix-config implementation work

After the Atlas and Lumio behavior is tested:

- install or link the intended Lumio revision on `macsp`;
- provide `ATLAS_URL` and `ATLAS_NODE_ID`;
- provision a secret token file through the existing secret-management mechanism;
- expose the variables to interactive pi sessions without committing secret values;
- avoid creating a permanent heartbeat service for an interactive session.

A background worker is a different runtime with a different lifecycle and should later receive its
own service declaration.

## Failure and recovery

| Failure | Required behavior |
| --- | --- |
| Atlas DNS/network unavailable | pi starts; integration reports disconnected |
| Authentication rejected | stop rapid retries; show concise actionable status |
| Atlas restarts | next retry registers again and resumes heartbeat |
| pi exits uncleanly | Atlas marks session offline after TTL |
| Duplicate startup hook | only one heartbeat loop per session |
| Slow Atlas response | request times out without blocking the TUI |
| Malformed configuration | integration disabled with one clear diagnostic |

## Privacy and security

Registration metadata must not contain:

- prompts or conversation content;
- repository file contents;
- absolute working-directory paths;
- usernames or browser state;
- environment dumps;
- API keys, cookies, or bearer tokens.

Tailscale provides network reachability control but is not a replacement for the Atlas bearer
token.

## Verification

### Atlas

```bash
uv run pytest -q tests/test_agents_service.py tests/test_agents_api.py
uv run pytest -q
uv run ruff check .
```

### Lumio

```bash
npm run check
```

Add focused tests with a fake Atlas HTTP server for successful registration, timeouts, rejected
authentication, retry, cancellation, and redaction. The tests must not require AMAX.

### nix-config

Run the repository's formatting/evaluation checks and build the affected macOS configuration
without switching it first.

### End-to-end acceptance

- Starting a Lumio-enabled pi session creates one visible Atlas agent.
- The record contains the declared protocol and software versions.
- `last_seen_at` advances while the session remains active.
- Atlas reports the session offline within the configured TTL after pi exits.
- Atlas restart is recovered without restarting pi.
- Atlas unavailability never prevents local Lumio use.
- No secret appears in Git, logs, process arguments, or Atlas metadata.

## Rollout order

1. Stabilize and deploy the current Atlas source under the correct `atlas.main:app` entry point.
2. Keep the canary isolated to a localhost systemd user service and a detached `4b79af1`
   rollback worktree, not the old `atlas_console` process.
3. Implement the Lumio adapter against a fake Atlas server.
4. Test against AMAX Atlas manually.
5. Add the minimal `nix-config` configuration.
6. Run the end-to-end acceptance checks.
7. Change this RFC status to `Implemented` and record the three deployed revisions.
